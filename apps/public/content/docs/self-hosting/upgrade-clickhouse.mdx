New installs run ClickHouse **26.3 LTS** (`clickhouse/clickhouse-server:26.3.67.30`). Installs created earlier keep the version in their `docker-compose.yml` until you change it: `openpanel upgrade` never touches the ClickHouse image. `openpanel doctor` tells you when yours is older than the supported release.

OpenPanel keeps working on older ClickHouse releases, but ClickHouse fixes only its three latest stable releases and its two latest LTS releases. 25.10 is no longer among them. 26.3 is supported until ClickHouse ships its next LTS release, expected in March 2027.

<Callout type="warn">
The upgrade is one-way. Once a newer ClickHouse has written to the data volume, an older one cannot read it. The way back is the backup you take in step 2, so do not skip it.
</Callout>

## Why 26.3 and not a newer release

From 26.6, ClickHouse's x86 image needs a CPU with AVX2: Intel Haswell (2013) or later, AMD Excavator (2015) or later. On an older CPU, such as an Ivy Bridge Xeon, a newer image crashes as soon as it starts. 26.3 is the newest LTS release that runs on a CPU without AVX2. Check your CPU:

```bash
grep -c avx2 /proc/cpuinfo
```

`0` means no AVX2: stay on 26.3. ClickHouse publishes its build without AVX2 (`amd64compat`) as a separate binary and has no Docker image of it, so when 26.3 leaves support such a machine needs newer hardware or an image you build around that binary.

If your CPU has AVX2, you can run `clickhouse/clickhouse-server:26.8.42.13` instead; OpenPanel's tests pass on it. Read [Memory on a shared host](#memory-on-a-shared-host) first.

## Before you start

- About 15 minutes, most of it the backup. The dashboard is unavailable while ClickHouse is stopped.
- Free disk space for one compressed copy of the ClickHouse volume.
- Your current version:

```bash
docker compose exec op-ch clickhouse-client --query "SELECT version()"
```

Tracking keeps working during the upgrade: the api accepts events into Redpanda while ClickHouse is down, and the worker writes them once it is back. Meanwhile `op-api` reports itself unhealthy, which is expected; Caddy keeps sending it traffic.

<Steps>
<Step>

### Stop the worker and ClickHouse

Run these in the directory that holds your `docker-compose.yml`. Note any detached parts first, so you can tell old ones from new ones after the upgrade:

```bash
docker compose exec op-ch clickhouse-client --query "SELECT database, table, reason, count() FROM system.detached_parts GROUP BY ALL"
docker compose stop op-worker op-ch
```

</Step>
<Step>

### Back up the ClickHouse volume

Find the volume's full name (Compose prefixes it with the project name), then archive it while ClickHouse is stopped:

```bash
docker volume ls --filter name=op-ch-data
docker run --rm -v <project>_op-ch-data:/data -v "$PWD":/backup alpine tar czf /backup/op-ch-data-backup.tgz -C /data .
```

</Step>
<Step>

### Change the image and start ClickHouse

In `docker-compose.yml`, set the `op-ch` image:

```yaml
op-ch:
  image: clickhouse/clickhouse-server:26.3.67.30
```

Then pull it and start ClickHouse:

```bash
docker compose pull op-ch
docker compose up -d op-ch
```

</Step>
<Step>

### Check it, then start the worker

```bash
docker compose exec op-ch clickhouse-client --query "SELECT version()"
docker compose exec op-ch clickhouse-client --query "SELECT database, table, count() FROM system.detached_parts GROUP BY ALL"
docker compose up -d op-worker
```

The first query prints `26.3.67.30`. If `op-ch` keeps restarting instead, read `docker compose logs op-ch`, and check the CPU as shown above when you moved to a release newer than 26.3. The second query should print the same as before the upgrade; a new row means ClickHouse could not load a part. `op-worker` starts once `op-api` is healthy again, usually within a few seconds. Open the dashboard and check that your charts show data.

</Step>
</Steps>

## Memory on a shared host

This applies only from ClickHouse 26.5, so not to 26.3. From 26.5 and 26.6, ClickHouse adapts to the memory free on the machine, which matters when it shares a host with the rest of the stack:

- A query runs on fewer threads while free memory is short, about one thread per `max_threads_min_free_memory_per_thread` (1 GiB by default) of free memory. On a test machine with 1 to 2 GiB free, heavy charts on 26.8 took two to two and a half times as long as on 25.10.
- The server's memory limit follows the memory the kernel reports as available, so ClickHouse leaves room for Postgres, Redis and Redpanda instead of growing until the kernel kills a process.

Check how much memory is free while the stack runs:

```bash
docker compose exec op-ch clickhouse-client --query "SELECT formatReadableSize(value) FROM system.asynchronous_metrics WHERE metric = 'OSMemoryAvailable'"
```

If that is only a few GiB and charts got slower, add more memory, or lower the per-thread requirement in `clickhouse/clickhouse-user-config.xml`, inside `<profiles><default>`:

```xml
<max_threads_min_free_memory_per_thread>268435456</max_threads_min_free_memory_per_thread>
```

Only do this on 26.5 or later: 26.3 and older do not know the setting and refuse to start.

## Going back

If something is wrong, put the backup back and return to the image you had. Never start the old image on a volume the new one has written to. Depending on the release, the old server either refuses to start, or starts and sets aside the parts the new one wrote as broken, so recent data silently disappears from your charts.

```bash
docker compose stop op-worker op-ch
docker run --rm -v <project>_op-ch-data:/data -v "$PWD":/backup alpine sh -c "find /data -mindepth 1 -delete && tar xzf /backup/op-ch-data-backup.tgz -C /data"
```

Set the `op-ch` image back to your previous tag, then `docker compose up -d op-ch op-worker`. Events tracked after the backup was taken are not in the restored data.

## Coolify

The Coolify template now ships ClickHouse 26.3. Its earlier `24.3.2` image cannot run OpenPanel's migrations, so an install on it never finished setting up. A Coolify install that does run on an older ClickHouse follows the same steps: back up the `opch-data` volume, then change the `opch` image.
